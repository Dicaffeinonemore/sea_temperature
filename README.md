### 1. `AGENTS.md`: 팀 작업 규칙

**① 담당자 규칙 (가장 중요)**
- 다른 팀원의 파일은 **읽기만** 합니다. 고치려면 사용자의 명시적 승인이 필요합니다.
- 파일을 고치기 전에 `docs/OWNERSHIP.md`에서 담당자를 확인합니다. 표에 없으면 `git log`로 작성자를 확인합니다.
- 담당자가 다르거나 모르면 수정·삭제·이름 변경·이동을 하지 않습니다. 바꿀 내용, 이유, 담당자 이름을 보여 주고 승인을 기다립니다.
- 안 쓰는 것처럼 보여도 팀원의 코드·테스트·문서를 지우거나 "정리"하지 않고, 대신 알려 줍니다.
- `reset --hard`, 강제 푸시처럼 다른 사람의 작업을 날리는 git 명령은 쓰지 않습니다.
- 공용 코드를 고치기보다 새 파일이나 내 구역에 추가합니다.

**② 말투와 언어**
- AI는 한국어로, 결과부터 답합니다.
- README·문서·화면 문구·커밋 메시지는 한국어로 씁니다. 코드 주석은 화면 파일은 한국어, 파이썬은 영어로 씁니다. 변수·함수 이름은 영어입니다.

**③ 코드 품질**
- 요청한 것만 합니다. 요청하지 않은 기능·리팩터링·파일·문서는 만들지 않습니다.
- 기존 코드를 먼저 읽고 같은 방식을 따릅니다. 표준 라이브러리로 되는 일에 새 패키지를 넣지 않습니다.
- 쓰지 않는 코드, 주석 처리된 코드, 빈 TODO를 남기지 않습니다.
- 오류를 덮어 버리거나 가짜 대체값을 만들지 않습니다.
- 없는 API·테이블·패키지 이름을 지어내지 않습니다.
- 테스트를 돌려 보지 않고 "완료"라고 하지 않습니다. 못 돌렸다면 그렇다고 말합니다.

**④ 보안**
- 비밀번호·키·개인정보(이름, 생년월일, 전화번호)를 코드에 적거나 로그에 남기지 않습니다.
- `.env` 파일은 읽거나 커밋하지 않습니다. DB 계정은 각자 `backend/backend/.env`에만 둡니다.
- 브라우저는 DB에 직접 접속하지 않고 FastAPI 백엔드를 거칩니다.
- 공용 DB에 `DROP`·`DELETE`·`ALTER` 같은 위험한 명령은 승인 없이 쓰지 않습니다. 스키마 변경은 DB 서버 관리자가 합니다.

**⑤ Git**
- 요청받았을 때만 커밋합니다. 푸시나 기록 변경은 승인을 받습니다.
- 내 fork에서 화면·기능별 브랜치로 작업하고 팀 저장소로 PR을 보냅니다.
- 커밋 전에 비밀정보가 없는지, 내 파일만 올라가는지 확인합니다.

**⑥ 실행·테스트**
- 백엔드: `backend/` 폴더에서 `..\.venv\Scripts\python.exe -m uvicorn backend.main:app --port 8000`
- 테스트: `py backend/run_tests.py` (DB 없이), `py backend/run_tests.py --db` (임시 스키마), `py -m unittest discover -s tests -v`

### 3. `DESIGN.md`: 디자인 공통 규칙 (초안)

- **아직 초안입니다.** `UNDECIDED`(미정)로 표시된 값(색, 글꼴, 간격 등)은 승인되지 않았습니다. 임의로 정하지 말고 후보를 제안해 승인을 받습니다.
- **우선순위:** 사용자 목표 달성 → 쓰기 쉬움·접근성 → 정보 구조·흐름 → 상태 설계 → 완성도 → 장식 순입니다. 위의 것을 아래 것 때문에 희생하지 않습니다.
- **화면 원칙**
  - 화면마다 주요 버튼은 하나만 둡니다.
  - 모든 것을 카드로 감싸지 않습니다.
  - 색만으로 의미를 구분하지 않습니다.
  - 글자 대비는 4.5:1 이상으로 합니다.
  - 브라우저를 200%로 확대해도 깨지지 않아야 합니다.
- **상태:** 데이터를 보여 주는 화면은 불러오는 중, 비어 있음, 오류, 성공 상태를 모두 만듭니다.
- **접근성:** WCAG 2.2 AA 기준이고, 폭 320px에서도 가로 스크롤이 없어야 합니다.
- **장식 기준:** 그라데이션, 유리 효과, 과한 그림자 같은 장식은 이유를 다섯 가지 질문으로 설명할 수 있을 때만 씁니다.
- **저작권:** 아이콘·이미지·글꼴은 쓰기 전에 `docs/design/ASSET_LICENSES.md`에 라이선스를 기록합니다. 참고한 디자인은 베끼지 않고 `docs/design/REFERENCE_LOG.md`에 기록합니다.
- **지금 쓰는 값(미승인):** 글꼴은 Noto Sans KR, 강조색은 `#1f5ae0`, 최대 폭은 420px입니다. 일관성을 위해 이 값을 쓰되, 확정은 승인 후 기록합니다.

### 4. `LAN_SETUP.md`: 팀 공용 DB 접속

- 같은 공유기(내부망)에 있는 팀원은 서버 PC 한 대의 DB에 접속합니다. 각자 PostgreSQL을 설치할 필요가 없습니다.

- 기본 권한은 **조회만** 가능합니다. 데이터 쓰기 권한은 계정을 만들 때 따로 받아야 합니다.
- 팀원 PC에서 FastAPI를 돌리려면 `team.env.example`을 `.env`로 복사하고 본인 계정과 비밀번호를 적습니다.
- 접속 확인: `Test-NetConnection 192.168.0.96 -Port 5432`의 결과가 `TcpTestSucceeded=True`면 됩니다.
- 서버 PC가 켜져 있어야 하고, 팀원은 `init-db`나 백업 복원을 실행하지 않습니다.

## HTML 버전

화면은 팀원별로 새로 구성하는 중입니다. 시작·양식장 등록·로그인·회원가입 화면(`app.html`)은 삭제했고 새로 만들 예정입니다. 아래 파일들이 같은 폴더에 있어야 합니다. 화면(기능)별로 파일이 나뉘어 있어 담당자가 자기 화면만 데이터에 연결할 수 있습니다.

| `home_test.py` | 홈 화면 + 홈 API를 한 번에 띄우는 서버. `http://localhost:8000/?customer=C-001` | DB 접속은 `DATABASE_URL` |
| `backend/` | 보험·지원제도 API (FastAPI, 아래 참고). 지금은 이 API를 쓰는 화면이 없음 | DB `insurance`·`gov24` 스키마 |

| `common.css`, `common.js` | **모든 화면 공통** 하단 바(홈·수온·대응 요령·보험·내 정보) | – |

### 공통 하단 바 쓰는 법 (새 화면을 만들 때 필수)

하단 바는 화면마다 만들지 않고 `common.css`·`common.js` 한 곳에서 관리합니다. 각 화면에는 아래만 넣으세요.

```html
<head>
  …
  <link rel="stylesheet" href="common.css">
</head>
<body>
  …
  <nav id="tabbar" data-active="insurance"></nav>  <!-- 지금 화면의 탭 -->
  <script src="common.js"></script>
</body>
```

- `data-active`: `home` · `temp`(수온) · `response`(대응 요령) · `insurance`(보험) · `me`(내 정보) 중 하나. 그 탭이 선택 상태로 표시됩니다.
- 화면 전체를 `.screen`(세로 flex) 안에 넣는 페이지는 `<nav id="tabbar">`를 `.screen`의 마지막 칸으로 두면 맨 아래에 붙습니다. 그 밖의 페이지는 화면 아래에 고정되므로 본문 아래 여백(약 104px)을 두세요.
- 탭 이름·링크·아이콘은 `common.js`의 `TABS`에서만 고칩니다. 링크가 `null`인 탭(지금은 수온·내 정보)은 화면이 생기기 전까지 "준비 중" 안내만 보여 줍니다. 대응 요령·보험 탭은 이전 화면(`response.html`·`insurance.html`)을 삭제해서 새 화면을 만들 때까지 열리지 않습니다.
- 디자인은 `home.html`(홈 화면 v2) 기준입니다. 각 화면에서 하단 바 스타일을 따로 덮어쓰지 마세요.

- HTML 버전은 Streamlit 버전과 별개입니다. `app.py` 수정이 자동 반영되지는 않습니다. HTML의 `<style>`은 디자인, `<section>`은 화면 항목, `<script>`는 동작을 담당합니다.


### 백엔드 실행

1. `backend/backend/team.env.example`을 같은 폴더에 `.env`로 복사하고 `DB_USER`·`DB_PASSWORD`에 **본인 팀 계정**을 적습니다. `.env`는 깃허브에 올라가지 않습니다. 비밀번호를 단톡·캡처에 노출하지 마세요.
2. 해당 계정에 `insurance` 스키마 조회 권한이 있어야 합니다(없으면 503). 권한은 스키마 소유자(nifs_team2)나 서버 관리자가 부여합니다.
3. 프로젝트 최상위 폴더에서:

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend\backend\requirements.txt
cd backend
..\.venv\Scripts\python.exe -m uvicorn backend.main:app --port 8000
```

4. `http://127.0.0.1:8000/docs`에서 API를 직접 눌러 볼 수 있습니다. 화면은 `python -m http.server 8765`로 열고 `http://localhost:8765/home.html`을 엽니다. localhost·127.0.0.1 주소는 CORS 허용되어 있고, 다른 주소는 `.env`의 `CORS_ORIGINS`에 추가합니다.

## 실행

```powershell
py -m pip install -r requirements.txt
py -m streamlit run app.py
```

Streamlit 등록 화면은 고객 API를 통해 선택한 품종과 양식장 정보를 저장합니다. 별도 터미널에서 백엔드도 실행하세요.

```powershell
py -m pip install -r backend/backend/requirements.txt
py -m uvicorn backend.main:app --app-dir backend --reload --port 8000
```

백엔드는 `backend/backend/.env`의 DB 설정을 사용합니다. 프론트의 API 주소는 `NIFS_API_URL`로 설정하며 기본값은 `http://127.0.0.1:8000`입니다. 새 DB의 품종 초기 데이터는 [고객 API 안내](backend/CUSTOMER_API.md)에 따라 입력합니다.

## 화면 흐름

시작하기 → 양식장 등록 → 비회원으로 오늘의 위험정보 이용

선택 경로: 좌측 상단 로그인 → 로그인 화면 → 회원가입 → 가입 정보 입력 → 오늘의 위험정보

- Streamlit 버전은 비회원 양식장 등록, 회원가입, 로그인·로그아웃을 실제 고객 API로 처리합니다. 회원가입 시 같은 고객 ID와 양식장·품종 연결을 유지합니다. 비밀번호는 서버에서 해시 처리해 저장합니다.
- 세션 토큰은 현재 Streamlit 세션에 보관합니다. 브라우저 재접속 복원과 SMS 본인확인은 아직 연결하지 않았습니다.
- 전복 선택 시에만 육상·해상 버튼이 나타납니다. `customer_service.species`의 `전복(육상)` 또는 `전복(해상)` ID를 선택해 `farm_species`에 저장하며, 별도 전복 구분 컬럼은 사용하지 않습니다.
- 위험정보 화면의 수온, 주의 단계, 추이, 예측은 모두 고정 예시입니다.
- 위험정보 화면의 지역 좌표 조회는 실제 `public.sigungu_area_coordinates`를 사용합니다. 시·군·구 → 읍·면·리/지역을 선택하면 위도·경도와 좌표 유형을 표시합니다. 등록 지역이 기본 선택되며 다른 지역 조회는 양식장 등록 정보를 수정하지 않습니다.
- 오른쪽 위 ☰ 버튼으로 사이드 메뉴를 열고 닫을 수 있습니다. 양식장 정보 수정은 작동하며 대응 안내·보험 비교·상담은 준비 중 화면으로 연결됩니다.

## 수동 확인

1. 백엔드 실행 후 DB의 지역·품종 목록이 표시되는지 확인합니다. 연결이 실패하면 등록은 진행되지 않습니다.
2. 양식 정보를 모두 선택하고 등록하기를 누르면 가입 없이 위험정보 화면으로 이동합니다.
3. 좌측 상단 로그인 → 회원가입으로 이동합니다. 빈 이름, 미선택 생년월일, 잘못된 전화번호, 8자 미만 비밀번호는 가입을 막는지 확인합니다.
4. 정상 입력 후 가입완료를 누르면 위험정보 화면이 표시됩니다. 로그인 화면의 비회원으로 계속 이용도 같은 화면으로 돌아가며 양식장 설정을 유지합니다.
5. 모바일 폭에서도 메뉴와 입력 항목이 잘리지 않는지 확인합니다.
